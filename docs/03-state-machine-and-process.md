# 状态机与核心流程

## 1. 设计原则

本项目是流程驱动系统，状态机是第一优先级设计对象。页面、接口、权限、消息都应围绕状态流转构建。

## 2. POI 主状态

说明：

- 本节包含项目完整规划状态机
- 当前代码实际已落地的状态子集见 `2.1`
- 阶段 3 以后如需接手开发，应优先以“当前已实现状态”理解系统

### 2.1 当前已实现状态（阶段 5）

| 状态 | 含义 | 允许进入方 |
|---|---|---|
| `DRAFT` | 采集草稿 | 采集者 |
| `SUBMITTED` | 已提交待核验 | 采集者 |
| `APPROVED` | 核验通过 | 核验者 |
| `REJECTED` | 核验不通过待整改 | 核验者 |
| `RESUBMITTED` | 整改后待复核 | 采集者 |
| `DISPUTING` | 争议处理中 | 采集者、核验者 |
| `ARBITRATING` | 最终裁定处理中 | 核验者、管理员 |
| `FINALIZED` | 已最终确认 | 管理员 |

## 4. 核心流程

### 4.1 采集流程

1. 采集者领取任务或主动新建采集
2. 拍照并获取定位
3. 填写分类、名称、描述
4. 提交采集记录
5. 系统生成待核验数据

### 4.2 核验流程

1. 核验者接收核验任务
2. 查看 POI 图片、位置、描述
3. 提交核验结论
4. 通过则进入 `APPROVED`
5. 不通过则进入 `REJECTED` 并生成整改单

### 4.3 整改流程

1. 采集者查看整改意见
2. 重新采集、补充材料或修改数据
3. 重新提交
4. 状态进入 `RESUBMITTED`
5. 再次回到核验流程

### 4.4 异议流程

1. 采集者不认可整改要求
2. 发起异议并补充说明
3. 核验者继续补充意见
4. 若无法达成一致，则升级到最终裁定

### 4.5 最终裁定流程

1. 管理员接收最终裁定任务
2. 查看历史采集、核验、沟通和争议记录
3. 必要时补充核查
4. 提交最终结论
5. 状态进入 `FINALIZED`

## 5. 关键业务约束

- 采集者只能修改自己负责或被退回的采集数据
- 核验者不能直接删除采集记录，只能给出结论
- 管理员最终裁定默认作为争议流程的最终结论
- 所有状态变更都必须写入操作日志
- 核验、异议、复核都必须绑定具体记录和说明
