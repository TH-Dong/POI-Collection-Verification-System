# 迭代计划

## 1. 阶段划分

| 阶段 | 名称 | 目标 |
|---|---|---|
| 阶段 0 | 项目定义与架构基线 | 明确需求、状态机、架构、数据库和规范 |
| 阶段 1 | 系统骨架与基础能力 | 搭建前后端工程和鉴权、上传等基础能力 |
| 阶段 2 | POI 采集最小闭环 | 打通采集者提交流程 |
| 阶段 3 | 核验与整改闭环 | 打通核验者审核与整改回传 |
| 阶段 4 | 地图查询与空间辅助 | 支持地图筛选、查看和导航 |
| 阶段 5 | 异议与最终裁定 | 建立争议升级和最终裁定机制 |
| 阶段 6 | 任务、通知与后台运营 | 建立任务分发、通知和配置能力 |
| 阶段 7 | 私聊、群聊与协作增强 | 增加实时沟通与经验交流 |
| 阶段 8 | OCR、微信与优化收尾 | 接入外部能力并完善体验 |

## 2. 阶段 0 的完成标准

- 需求边界明确
- 角色与职责清晰
- 状态机可落地
- 系统架构确定
- 数据库初稿完成
- API 和开发规范形成文档
- 后续阶段计划明确

## 3. 阶段 1 入口条件

开始阶段 1 前需确认以下事项：

- 前端技术栈采用 `React + React Native`
- 后端技术栈采用 `Spring Boot`
- 数据库、缓存、对象存储等基础设施选型已定
- POI 主状态和任务状态不再频繁调整
- 角色权限边界已初步确认

## 4. 推荐实施顺序

1. 系统骨架、鉴权、用户权限
2. 文件上传、附件管理、字典配置
3. POI 采集
4. 核验与整改
5. 地图能力
6. 异议与最终裁定
7. 通知、聊天、后台增强
8. OCR、微信和体验优化

## 5. 风险与控制

### 5.1 需求频繁变化

控制方式：

- 先冻结状态机和角色职责
- 阶段内不轻易改核心状态

### 5.2 地图与微信接入复杂

控制方式：

- 先保留适配层
- 业务流程先不依赖微信完成

### 5.3 协作消息带来复杂度

控制方式：

- 先实现系统通知
- 私聊与群聊放在后续阶段

### 5.4 阶段边界失控

控制方式：

- 每阶段只解决一个核心目标
- 先打通主链，再做增强功能
